# 昇腾 vLLM-Ascend 并行推理实验汇报口头稿

## 五分钟口头稿

领导好，我汇报一下这次在昇腾平台上使用 vLLM-Ascend 开展并行推理验证的结果。

这次任务主要有两个目标。

第一，验证流水线并行 PP 与张量并行 TP，或者专家并行 EP 组成的二维并行推理。
第二，验证流水线并行 PP 与 CPU 权重卸载的组合能力。

我的验证策略是先用 Qwen3-8B Dense 模型打通完整链路，再扩大到
Qwen3-30B-A3B MoE 模型验证专家并行。所有实验都使用真实模型权重，
没有使用 dummy 权重。

先说最终结论：本次预定的功能目标已经全部完成。

在 Qwen3-8B 上，我完成了 PP=2、TP=2 的二维并行验证。四个 rank 均正常建立
HCCL 通信，服务启动、首请求和短压测全部通过。随后进行了连续 30 分钟稳定性
测试，共完成 442 轮、7072 个请求，全部成功，没有出现 OOM、HCCL 超时或
worker 退出。

第二项是 PP 与权重卸载。这里采用的是 vLLM 的 prefetch 权重卸载后端，
不是 `cpu-offload-gb` 对应的 UVA 路径。prefetch 可以按层、按参数选择卸载，
并在计算前异步把权重预取回 NPU，更适合当前昇腾环境。

在 PP=2、TP=1、固定每个 NPU 16 GiB KV cache 的相同条件下，对比无卸载和
prefetch 卸载后，每个 rank 的 NPU 驻留权重从 7.6576 GB 降到 6.5326 GB，
下降 1.125 GB。平均每个 die 的 HBM 占用下降 857.5 MiB，worker 进程显存
下降约 859 MiB，同时容器主机内存增加约 3.89 GiB。这个结果证明权重确实
从 NPU 转移到了 CPU 侧，而不是仅仅接受了启动参数。

PP 加权重卸载也完成了连续 30 分钟稳定性验证，共 74 轮、1184 个请求，
全部成功，测试结束后服务仍然健康。

在 8B 路线打通后，我进一步使用 57 GiB 的 Qwen3-30B-A3B MoE 真权重验证
PP 与 EP。模型包含 128 个专家，每个 token 路由 8 个专家。最终配置为
PP=2、TP=2，并开启 EP，使用四个 NPU die。模型成功加载，四个 rank 完成
PP、TP 和 EP 通信初始化，首请求返回成功。16 请求短压测全部通过，输出吞吐
约为 49.7 tokens/s。

MoE 长稳测试第一次运行到约 26 分钟时，服务收到了外部终止信号。日志中没有
OOM、Python 异常栈或 HCCL fatal，Docker 容器也没有发生重启，所以这次结果
被记录为外部中断，不归类为模型失败。之后使用相同配置重新进行了完整测试，
共完成 85 轮、1360 个请求，全部成功。压测自然结束后，服务健康检查仍然返回
HTTP 200。因此，Qwen3-30B-A3B 的 PP×EP 功能和 30 分钟稳定性最终都已通过。

实验过程中还发现了两个需要重点说明的问题。

第一，共享服务器上的 NPU 资源会动态变化。30B 模型首次启动时，一个目标
NPU 只剩 14.73 GiB，低于默认显存策略要求的 49.02 GiB，因此启动前容量检查
失败。后续通过重新选择空闲 NPU，并固定每个 NPU 8 GiB KV cache，模型正常
启动。这说明大模型实验必须在启动前检查每个 die 的实际占用，不能只看设备
数量。

第二，当前 prefetch 配置虽然实现了明确的显存下降，但性能还没有达到生产
要求。在当前短请求负载下，group size 为 4、每组卸载 1 层的配置带来了较大
吞吐损失。因此目前的结论是：功能验证可以 GO，但当前卸载参数的生产应用
暂时 NO-GO。下一步需要降低卸载比例、调整 prefetch step，并按照真实业务的
输入长度、输出长度和并发重新测试。

最后总结一下，本次已经完成三项有效签收：

第一，Qwen3-8B 的 PP×TP 二维并行通过；
第二，Qwen3-8B 的 PP+prefetch 权重卸载通过，并获得可量化的 NPU 显存收益；
第三，模型扩大到 Qwen3-30B-A3B 后，PP×EP 以及连续 30 分钟稳定性通过。

当前已经形成可复现的启动脚本、测试教程、故障处理记录和实验报告。后续工作
重点不是继续证明“能不能跑”，而是围绕权重卸载性能调优，以及根据目标业务
负载形成可用于生产决策的参数组合。

我的汇报完毕。

## 一分钟精简版

本次在昇腾 vLLM-Ascend 上完成了两条核心路线，并进一步扩大了模型规模。

Qwen3-8B 的 PP=2、TP=2 二维并行验证通过，30 分钟内完成 7072 个请求，
成功率 100%。PP=2 加 prefetch CPU 权重卸载也验证通过：固定 KV cache 后，
每个 rank 的 NPU 驻留权重下降 1.125 GB，平均每个 die 的 HBM 下降
857.5 MiB，30 分钟内 1184 个请求全部成功。

随后扩大到 Qwen3-30B-A3B MoE 模型，完成 PP=2、TP=2、EP 开启的真权重验证。
短测吞吐约 49.7 tokens/s，完整 30 分钟重跑完成 1360 个请求，成功率 100%。

最终结论是：PP×TP、PP+权重卸载和 PP×EP 的功能及基础稳定性均已通过。
当前 prefetch 卸载虽然能够降低 NPU 显存，但短请求性能损失仍然较大，因此
功能验证可以 GO，现有卸载参数的生产应用暂时 NO-GO，下一步重点是调优卸载
比例和预取参数，并使用真实业务负载复测。

## 领导可能追问的问题

### 1. 为什么权重卸载没有使用 `--cpu-offload-gb`？

vLLM 有两类卸载后端。`--cpu-offload-gb` 主要配置 UVA 容量路径，本次使用的
是 prefetch 后端，通过卸载分组、卸载层数和预取步数控制。两者是替代关系，
不是必须同时提供。当前昇腾环境优先验证 prefetch，因为它支持按参数卸载和
异步预取。

### 2. 如何证明权重真的卸载了？

有三组相互印证的数据：每 rank 的 NPU 驻留权重下降 1.125 GB，固定 KV 后
平均 HBM 下降 857.5 MiB，主机内存增加 3.89 GiB。同时日志明确显示
`AscendPrefetchOffloader` 初始化以及卸载模块和静态 buffer 信息。

### 3. 为什么卸载后性能下降？

卸载减少了 NPU 常驻权重，但增加了 CPU 到 NPU 的数据搬运和计算等待。
当前配置每四层卸载一层，在短请求下数据搬运占比过高。后续需要减少卸载层数、
调整预取距离，并用更长输出和真实并发验证能否摊薄搬运开销。

### 4. PP×EP 是否真的使用了专家并行？

使用的是具有 128 个专家的 Qwen3-30B-A3B MoE 真权重，启动参数明确开启
expert parallel，日志记录了 world size=4 以及 PP、TP、EP rank 分配，
返回结果的系统指纹也包含 `tp2-pp2-ep`。

### 5. 目前能否直接用于生产？

并行功能和 30 分钟基础稳定性已经通过，但还不能直接得出生产可用结论。
尤其是当前 prefetch 参数的短请求性能损失较大，还需要业务数据集、目标并发、
长时间压力测试和参数调优。

### 6. B2 为什么没有执行？

B2 是 PP×TP 与 prefetch 三者同时开启的增强组合实验。当前任务的两个目标
已经分别由 A2 的 PP×TP 和 B1 的 PP+prefetch 完成签收，因此 B2 不影响核心
任务结论，可以作为后续优化阶段的补充验证。
